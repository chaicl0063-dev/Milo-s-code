# 官网空间真实性与路线常识检查

日期：2026-09-16；供 Claude 实现及 GPT 评审使用。  
目标：防止“照片是真的，但位置乱标”“路线来自应用，但未经合理性检查”的问题再次发生。本轮仅制定规则与核查证据，未改路线算法。

## 1. 原因与责任

此前错误来自三条断链：
1. 把地标身份真实，误当成拍摄位置、YOU 点和连线也真实。
2. 把地图当成可自由排版的插图，为了摆卡片手写 x/y，而没有保持地理关系。
3. 把“应用真实输出”“tsc 通过”“无横向溢出”当成结果合理的证明。

这些是实现者和评审者应主动识别的问题，不应等用户指出。修正方式不是给模型多一句“注意常识”，而是让照片、坐标、距离与路线各有明确来源，并在实现前检查相互关系。

## 2. 本轮补查：不要把展示错误与路线算法混为一谈

已读取 lib/plan.ts、lib/planCore.ts、lib/route.ts、scripts/fixtures/route-paris-1h.json，并结合前轮查过的 CityMap、Explore、content。

- 官网 ROUTE 的点位为手写百分比，CityMap 是任意几何街区；不是经纬度投影。这足以确认展示层不能证明地理正确。
- 应用 orderByNearest 已按“从当前站走向剩余最近站”排序，buildPlan 会调用它。
- 该距离使用 haversine（两点地表直线距离），没有在所查规划链路中使用步行路网。因此无法证明过河、入口、围墙、道路可通行性和实际绕行。
- 最近邻是一种简单排序，不保证总路线最短；“每一步最近”也不是所有旅游路线的唯一合理标准。
- 真实样例三段约 116+17+244=377m；按保存坐标重新计算未逐段取整，总计约 378m。
- 同一出发点、不返回起点、不考虑道路与其他约束，枚举三站六种顺序：1→2→3 约378m；1→3→2 约588m；2→1→3 约372m；2→3→1 约599m；3→1→2 约402m；3→2→1 约419m。1=Place du Châtelet，2=Fontaine du Palmier，3=Rue des Lombards。
- 这说明当前样例在直线距离下不是明显舍近求远；但不能据此断言真实步行路线合理。本轮未查真实路网，不作实际导航结论。
- 样例每站停留15分钟，共45分钟，步行估计5分钟；现代码加10%及5分钟缓冲，得到60分钟，内部时间口径可解释。但广场与其中喷泉约17m，是否值得各占15分钟仍需内容/游览价值评审，不能只靠凑够三站。

上一轮将 fixture 视为可靠内容源的判断在此补充：它能证明来源，不能自动证明质量。官网“about 0.4 km”源于直线分段估算，不应无说明地当作实测步行距离。

## 3. 实施前先交一张事实表

仅一张表，不另建繁琐审批系统：

| 对象 | 必填依据 | 不能确定时 |
|---|---|---|
| 照片 | 真实地标、来源、视角、横竖裁切 | 不标未知主体或空间关系 |
| YOU | 示例起点/实际位置、坐标；若在照片上还需拍摄位置和地面对应依据 | 放非摄影的信息区，或不画 |
| 地标标记 | 对应哪栋可见建筑、锚点位置 | 不用附近地名冒充画面内建筑 |
| 地图点 | 稳定地点 ID、经纬度、坐标系统、投影方式 | 不随意估 x/y |
| 距离 | 从哪里到哪里；直线估算还是步行路网；单位和时间 | 写清估算口径或不显示 |
| 连线 | 站序还是可行走道路路径 | 站序单独表达，不伪装导航 |
| 时长 | 各段交通、停留、缓冲的来源和求和 | 不把时间预算当测得时长 |

任何依赖字段为空，不得用“示例”二字补齐事实；采取局部降级，其他工作继续。

## 4. 照片空间规则

- 用户站立位置不能落在屋顶、空中、墙面等不合场景的位置。
- 照片空间不是经纬度地图。即使有真实坐标，也不能直接线性映射成照片像素。
- 没有拍摄方向/姿态依据，不表现“系统知道镜头朝向”的连线或自动锁定。
- 能标地标，只证明画面里地标可辨认；不自动允许 YOU、距离或到地标的路径。
- 按钮卡片可以为排版移动；地标锚点必须随着真实照片裁切变换，不能所有断点共用未经验证的百分比。
- 换照片、裁切、object-position 或容器比例，触发所有锚点重新检查。
- 需要说明示例时，说明必须可见且覆盖整个演示范围；小字不能抵消画面本身的错误暗示。

## 5. 地图规则

- 经纬度是真相源；屏幕像素是投影结果。数据层保留地点 ID/坐标，渲染层计算像素。
- 底图与点位采用一致的坐标基准；不混用不同坐标系统而不转换。
- 固定地图可以使用有来源的静态底图；交互地图可复用现有能力。都必须有正确地理对应和来源署名。
- 地理点不为卡片让位。只移动卡片，用引线连接真实点；近邻可聚合或用编号配列表。
- “站序图”允许抽象排布，但不配真实道路名称和精确距离暗示比例；“真实地图”则保持位置与道路关系。两种都能做漂亮，不能混淆。
- 道路线没有数据就不画。跨河必须沿真实可行桥梁，不能直穿水面/建筑并称步行路线。

## 6. 路线常识检查

先区分三个目标：短距离、少折返、旅游体验。三者不总一致。若因为入口、单行通道、开放时间、预约或兴趣而先远后近，可以合理，但必须有依据；不能一律最近优先，也不能无理由绕行。

对官网选用的一条样例，逐站检查：
1. 点位是真实可到访位置还是建筑中心/道路中心？入口与步行起点是否合理？
2. 实际道路能否走通？有河流、围墙、关闭道路、收费区或高差吗？
3. 同一组站点、不额外加终点要求时，与更短顺序相比是否明显绕行？若要求回起点，比较双方都必须回起点。
4. 是否来回经过同一条路，却没有解释？
5. 广场和广场内喷泉是否应作为同一停留区的两个看点？不为凑站数重复停留。
6. 距离口径、步行分钟、停留和缓冲能否加总？“一小时预算”不能冒充整条路线实测恰好60分钟。
7. 若路网尚未接入，只显示明确的站序示例与时间估计，不承诺最短/最佳/逐街导航。

对算法的后续改进建议应单列应用任务：小规模站点可比较全部顺序或作局部优化；有路网数据时用步行成本矩阵。不能为了修官网展示，悄悄改业务算法或新增收费地图服务。

## 7. 可执行检查与回归案例

Claude 对修改相关部分增加有价值的检查：
- 任意屏宽下地理点来源仍是同一坐标，不能恢复手写百分比地理位置。
- 近邻标签重叠时只移标签；地理点不变。
- 直线距离不得被格式化成“已核实步行距离”。
- 三站案例对比全部顺序；出现明显额外绕行要检查理由，不能只检查数组长度。
- 跨河但近岸无桥、围墙两侧直线很近、入口在建筑另一侧、广场包含喷泉、指定返程、照片横竖裁切，作为人工或自动回归场景。
- 地理身份、视角和路径可达性无法仅靠类型测试判断，需人工检查真实照片/地图证据。

## 8. 每轮交付的最小证据

在现有 COLLABORATION 实现记录中附：
- 一张事实表；
- Hero 桌面与手机截图，关键锚点可见；
- 一张实际地图与点位核对图，或明确标记为非地理站序图；
- 路线距离口径、总时间分解、绕行/近邻重复判断；
- 未核验项和采用的降级处理。

先查“人能否站在这里、地点是否在这里、路是否能这样走”，再查“是否像目标样张”。技术测试、设计观感和现实合理性三者都应检查，互不替代。
