# 官网 V2 方向诊断与修正建议

日期：2026-09-16  
对象：Milo 判断方向；Claude 据此安排下一轮工作。  
性质：基于现有文件、目标图及截图的完整诊断。建议不等于用户已批准改版；本轮没有修改页面代码、生成新配图、提交或发布。

## 1. 结论

新版的产品定位与浅色蓝色方向仍然成立，工程结构也可保留。偏移发生在“城市图层”如何被实现，以及每轮验收如何判断结果：

**最初要呈现的是“站在街上，选中眼前的地方，听一句故事，再继续走”；现在更像“真实地标大图，加上一组状态卡和多段产品说明”。**

这不是简单少几张新图，也不是加上动画就能解决。建议继续停在静态阶段，先修事实表达与遮挡问题，再只做 Hero 的桌面、手机两个版本作为下一轮样张。通过后沿现有段落顺序收紧后续内容，不重新做九屏规格书。

## 3. 根因：为什么每轮都在修，整体仍会偏

### R1. 参照图从“视觉关系”被拆成了“元素清单”

B 图最有用的是：街头行人的尺度、真实环境与产品卡的融合、紧凑的横向阅读、照片与信息的主次关系。现在大量保留的是坐标、蓝点、状态格、卡片、波形等零件。

代码直接体现了这种转译：Hero.tsx:14 仍是固定左侧约 500px 文案区与右图的网格；四块 Tile 占单独两行；产品演示全部位于右侧照片内。使用网格本身没有错，问题是两部分没有形成共同的视觉重心。

B 图的四个元数据格横向紧凑排列；现版桌面 2×2、手机也 2×2，视觉重量上升。数据更多不自动等于产品更清楚。

同时，B 图自身包含不可照搬的地名、距离、地图线路及应用没有的控件。不能把整张生成图当作事实与交互规格。应保留它的视觉关系，按真实能力重新组织信息。

### R2. 后续修补改变了画面基础，却继续沿用“Hero 已通过”的结论

28.2 记载 Phase 1B 视觉通过，这是应尊重的历史决定。此后 B3 把 AI 街景换成真实塔图，B4 又删去了多地点路线。这两项都影响了画面的主体与叙事，不能仅以“构图未变”认定视觉效果也未变。

现用照片能证明所示地标，但高处远眺、夕照、缺少街头人物尺度，与 Brief 要求的眼平街景和“我正站在这里”存在明显落差。Hero 的 YOU 点落在屋顶/高处画面区域，细线仍将它与塔连接。

因此：事实修正是必要的；修正后的构图需要重新验收。“同一张真实照片”并不能证明任意放置的 YOU、拍摄方向与距离都正确。

### R3. 最重要的手机验收被“没有横向滚动”替代

375×812 首屏里，标题、副题、两个按钮、浏览器说明和四块 Tile 先占据主要空间。照片约在 y=643 CSS px 开始，首屏只能看到塔顶，地点卡、播放区与 Mia 回答还在下方。

这与“3–5 秒理解产品”“移动端 CTA 后进入产品/地点体验”的目标不符。B2 已要求状态卡不能压过首屏，实施只缩小了卡片，没有改变它们排在演示之前的优先级。

脚本只比较根节点 scrollWidth 与 innerWidth；SiteV2Landing 又使用 overflow-x-clip，照片容器也有 overflow-hidden。内部标签被裁掉时，根节点依然可能报告无溢出。截图中已经发生了这种情况。

### R4. 静态展示、可操作演示和真实产品状态混在了一起

Hero 的 Pause、Speaking，SeeHear 的输入框/Send，Explore 的 Map/List 都是静态元素；ui.tsx 的 PlayButton 返回 span，MapListToggle 也是 span。Guides 的试听却是真按钮并调用现有语音逻辑。

静态阶段用示意界面本身符合 Brief，不能因此指责开发没做完整 App。但同一页面里相似控件有的能用、有的不能用，且 Hero/SeeHear 明示“正在说话”，访客容易尝试点击后认为产品失效。

需要确定清楚的演示方式：静态示例就近说明，实际可用入口明确；若之后选做真实试听，仅复用既有能力并让状态与声音一致，不以循环动画伪装播放。

### R5. “只查阻断项”的协作边界已经不覆盖当前问题

COLLABORATION 第 29 节限制 GPT 不讨论方向、不写文案、不出规格；29.5 把下一步安排成动画与换图。这适合已经稳定通过的页面，却不适合用户现在明确提出的“找跑偏根因、给调整建议”。

本轮用户最新要求优先，足以授权诊断和建议，无需再请求一次允许。另一方面，这也不意味着本报告能把所有建议直接标为用户批准。

最有效的调整是：GPT 给出证据和一轮有边界的修改任务；Claude 做一个可看的样张；Milo 看视觉结果。不要恢复“长需求书—长规格书—机械 QA”的旧链路。

### R6. 图片、内容和版式的依赖没有在交接中同步更新

28.2 的槽位表仍称 Hero 用 hero-1672/hero-portrait，后续代码实际已换为同一塔图；29.2 又笼统写“GPT 重出一套图”。这会让下一位协作者误以为生成一张漂亮城市图就能替换有实名地标的 Hero。

content.ts 自称全部事实和槽位集中于此，但 Ask.tsx 仍直接写 Tour Saint-Jacques · 120 m，Hero/Moment/Explore/Start 也有产品声明。仅审 content.ts 无法保证全页事实一致。

theme.ts 和 Manrope 已按方向接入，不是本轮主要矛盾。CityMap 的颜色、局部选中边框等仍有硬编码，但不值得为此先做设计系统重构。

## 4. 目标图与现版的关键差异

| 维度 | B 图值得保留的关系 | 现版证据 | 建议 |
|---|---|---|---|
| 使用情境 | 有行人、街道、近距离观看感 | Hero 为高处塔景；YOU 落在画面屋顶区域 | 真实街头视角优先；暂缺素材时不要把 YOU 强行放在照片上 |
| 产品重心 | 地点、音频、Mia 组成一个主要对象 | Hero 两张独立卡；状态格竞争注意力 | 合成一块紧凑的地点讲解单元，元数据降为辅助 |
| 密度 | 横向组织紧凑，主次仍清楚 | 以多卡、多段说明增加信息量 | 按理解顺序减重复，不再要求统一“加密 30%” |
| 手机 | B 图没有手机样张，不能直接推导 | 首屏尚未看到产品讲解 | 单独设计手机优先级，实拍第一视口 |
| 地图 | 细密地图底图、清楚站点 | 大块任意街区、固定百分比坐标 | 真坐标与示意顺序分清；不凭视觉想象补街道 |
| 全页节奏 | 主要产品片段紧密相接 | Moment、SeeHear、Ask 多次重述同一塔的背景 | 每段推进一个动作，减少重复事实与状态 |
| 氛围 | 明亮城市生活 | CityBreak 大面积较暗夕照 | 新氛围图向自然日光/较明亮街景调整；不增加 UI |

注意：B 图不含现版所有八屏内容，不能要求整页高度或段落逐像素一致；A 的手机外壳、手写字、偏青绿方向也不应重新带回。

## 5. 已确认问题与修复优先级

以下 BI 是具体问题，不将所有审美建议都包装成上线阻断项。

### BI-01｜地点标签裁切及覆盖（截图确认）

- 桌面 Moment：整页图中地点卡从照片左边被切断。Moment.tsx:25 的 overflow-hidden 与 :31 向识别框左侧偏移的固定宽卡片共同造成。
- 手机 Moment：地点卡压住左下坐标；同屏两个绝对定位层没有避让。
- 手机 Hero：Sample 角标与产品卡组都锚定 bottom-3，后渲染的卡组覆盖了示例说明；现有长图中该说明不可见。对应 Hero.tsx:90、:100。
- 修法：给卡片、照片主体、说明分别安排可见空间；窄屏采用正常文档流或独立信息带，不能仅在父级隐藏溢出。
- 验收：各约定宽度完整显示地名、示例说明，不遮挡照片关键部分和必要文字。

### BI-02｜邮箱保存失败仍声称已登记（代码确定，未实发请求）

PlusNotify.tsx:20–21 只检查 HTTP 成功后就进入 done；:27 声称已在名单。app/api/signup/route.ts:44、:56 在没有配置或存储失败时会返回 HTTP 200 与 stored:false。

因此存在可确定的错误成功路径；本轮没有验证线上是否配置存储，也没有提交邮箱。Claude 应在客户端检查响应 ok/stored，只有明确 stored:true 才声称登记成功，其余显示可重试状态。这不需要修改商业策略或存储架构。

### BI-03｜固定样例被呈现为访客当前状态（代码及截图确认）

Hero.tsx:44 的 Your location 使用固定巴黎坐标，旁边 Current area / Guide ready / voice on 同样是固定值。可见的 Sample 只位于照片内，桌面也不能清楚涵盖左侧状态，手机还被盖住。

建议把整个演示范围就近标为巴黎示例，固定地点/示例起点与访客真实位置分开。无需让官网获取访客定位来修文案。

Moment 的“Your guide has noticed the same one”与识别框还会暗示自动看见视线内建筑。应用确有用户主动拍照识别（GuideScreen.tsx:275），不能写成“没有识别功能”；应明确展示用户选点或提交照片这个动作，避免扩展成被动识别或相机方向定位。

### 待复核项｜不要冒充已实测缺陷

- Hero 在约 1024–1100 宽，右侧空间缩小而卡片仍为 left:50% + width:330px，存在被容器裁切的风险。已有评审图没有这个宽度，需要补拍确认。
- Explore 的 3 号站卡与右上街景照片在桌面有竞争/局部遮盖；手机长地名被 truncate。全名至少应在邻近的有序列表完整呈现，不能只剩省略号。
- Map/List、播放、追问等静态外观需要统一说明或入口策略；这是发布前要明确的演示体验，不要求本轮开发完整交互。
- 官网域名重写根路径时，如果 NEXT_PUBLIC_APP_URL 未配置，根入口可能回到官网。代码允许这种条件，本轮未核生产环境，不判定线上现已坏。
- 反馈邮箱在 brand.ts 注释中仍为待开通占位；实际可收信状态需上线前确认，本轮不擅自更换。

## 6. 合理调整范围

### 保留

产品定位、Mia/Milo、Around/Guide/Me、价格策略、路线逻辑、API、现有字体与蓝色系统、/site-v2 隔离结构，以及当前段落先后关系。

### 下一轮只重点调整 Hero

1. 手机顺序：标题与简短说明 → 主 CTA（次 CTA 降为轻链接）→ 地点/讲解演示 → 辅助状态。四块 Tile 不再占据演示前的空间。
2. 用一个紧凑的地点讲解单元承载缩略图、地名、音频示意与一句 Mia 内容；避免再增加悬浮卡。
3. 保留 B 的真实环境与信息层融合。不能把“融合”解释成必须把定位点放在任何照片上。
4. 若暂时没有合适的真实眼平照片，当前真塔图只作为地点照片使用；将示例起点移入非摄影的信息区，取消误导性的 YOU→塔空间线。此项相对 B4 是明确的视觉修订建议，需在样张中展示，不静默宣称原构图不变。
5. 先做一版推荐样张，手机 375×812 第一视口应看到地名、讲解/播放区域及 Mia 的至少一句短内容；不靠缩小到难读的小字硬塞。
6. 桌面仍展示同一个故事，不能通过不断增加元数据获得“科技感”。

### Hero 通过后再顺序收紧

- Moment：展示“选中/识别这个地点”的动作，裁切细节需与讲解所指内容对应；修标签避让。
- SeeHear → Ask：保持先听后问，一问一答优先用“应该看哪里”推进；关于教堂拆除的历史不用在 Hero、地点介绍、完整讲述、追问中逐次重复。段落可以保留，内容需各有作用。
- Explore：保留三站、一小时及现有业务逻辑。最小修法是在组件附近明确示例、让站序与地理路径分开，并移走遮挡卡片的氛围图。若继续强调地图，则用 fixture 真经纬度投影或现有地图能力；不给任意 x/y 配真街名。连线只表示顺序，不生成沿街导航。第一、二站很近，可用引线排标签，不挪动真实点位来凑版式。
- Guides：保留已实现的真实试听。手机避免肖像占去过多宽度，使长代表句形成窄文本柱；优先重排头像/名字行与下方全宽句子，不先换人设或音频。
- CityBreak：只作为短暂换气，选更明亮、有人在街上行走的氛围图。
- Start：收尾 CTA 保持突出；地图选点等手机独有缺失信息可通过前文简短表达补齐，不为补齐而恢复整块重复状态板。

## 7. 图片交接原则

“重新生成一套图”不能作为所有槽位的统一解法。

| 槽位 | 约束 | 下一步 |
|---|---|---|
| STREET.hero | 若标圣雅克塔，必须是真实匹配照片；同时适合街头尺度和 UI 留位 | 先确认构图，再找/选真实眼平素材；现塔图可临时作为地点照片 |
| PLACE.photo/detail/thumb | 真实地点证据；裁切要看得出讲解所指细节 | 保留来源登记，分别验收横竖裁切，不只换文件 |
| STREET.walk | 可用 AI 虚构氛围图 | 画面有人行尺度，避免贴到实名站点卡旁让人误认成该站照片 |
| GUIDES images | 两位角色身份一致 | 现阶段可保留，不为“全套换图”制造额外返工 |
| CITY_BREAK | 可用 AI 氛围图 | 明亮自然、街头生活，桌面横图与手机竖裁切均成立 |

以后由 GPT 制作的新配图及交接材料，也放在本项目 docs 下交付；Claude 如需接入 public/images，应在日志记录对应关系。不要让生成图承担真实地标照片、地图几何或应用截图的证明作用。
